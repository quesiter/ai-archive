## 1. 部署形态

| 服务 | 作用 | 对外端口 |
| --- | --- | --- |
| app | migration、Fastify API、React 静态资源 | 仅 `127.0.0.1:${ARCHIVE_PORT:-18080}` |
| worker | PgBoss 消费、Cron、导入、Restore、完整性检查和 housekeeping | 无 |
| postgres | PostgreSQL 17 与 PgBoss | 仅 `127.0.0.1:${POSTGRES_PORT:-15432}` |
| host-monitor | cgroup/文件系统指标 | 仅 Compose 网络 expose 9091 |

生产入口应由反向代理提供 HTTPS。系统按单实例、单管理员运行；仓库没有多节点编排。

## 2. 群晖 NAS 全新安装

推荐 DSM 7.2.2、Container Manager 和 x86-64。创建目录：

```sh
mkdir -p /volume1/docker/ai-conversation-archive/source
mkdir -p /volume1/docker/ai-conversation-archive/data/postgres
mkdir -p /volume1/docker/ai-conversation-archive/data/imports/inbox
mkdir -p /volume1/docker/ai-conversation-archive/data/imports/processed
mkdir -p /volume1/docker/ai-conversation-archive/data/imports/failed
mkdir -p /volume1/docker/ai-conversation-archive/data/restores
chown -R 1000:1000 \
  /volume1/docker/ai-conversation-archive/data/imports \
  /volume1/docker/ai-conversation-archive/data/restores
chmod -R u+rwX,go-rwx \
  /volume1/docker/ai-conversation-archive/data/imports \
  /volume1/docker/ai-conversation-archive/data/restores
```

解压源码到 `source`，然后：

```sh
cd /volume1/docker/ai-conversation-archive/source
cp deploy/.env.synology.example deploy/.env
openssl rand -hex 24
openssl rand -base64 32
```

分别写入 `POSTGRES_PASSWORD` 和 `APP_MASTER_KEY`，设置真实 HTTPS `APP_ORIGIN`。主密钥必须解码为恰好 32 字节并离线保存；丢失后无法解密 TOTP、LLM API Key 和 SMTP 密码。

启动：

```sh
cd /volume1/docker/ai-conversation-archive/source/deploy
docker compose --env-file .env build
docker compose --env-file .env up -d
docker compose --env-file .env ps
curl -fsS http://127.0.0.1:18080/healthz
```

app 在启动 API 前顺序执行 migration 0000–0021。健康响应应包含 `ok=true` 和 `version=V2.3.0`；app、postgres、host-monitor 为 healthy，worker 为 Up。

## 3. 环境变量

| 变量 | 默认/要求 | 影响 |
| --- | --- | --- |
| `NODE_ENV` | production | 生产安全校验和 Cookie 行为 |
| `APP_ORIGIN` | 生产必填；非本机必须 HTTPS | Cookie、CORS、CSRF 同源、报告链接 |
| `APP_MASTER_KEY` | 生产必填，32 字节 Base64 | TOTP/Secret 加密和备份指纹 |
| `DATABASE_URL` | Compose 注入 | 应用和 Worker 数据库连接 |
| `POSTGRES_DB/USER/PASSWORD` | 密码必填 | PostgreSQL 初始化 |
| `ARCHIVE_DATA_DIR` | `./data` | PostgreSQL 和 import 持久目录 |
| `ARCHIVE_PORT` | 18080 | app 本机绑定端口 |
| `POSTGRES_PORT` | 15432 | PostgreSQL 本机绑定端口 |
| `ARCHIVE_IMAGE` | ai-conversation-archive:latest | 四服务镜像 |
| `TRUST_PROXY` | false | 可信代理，可为 true/跳数/表达式 |
| `EXTENSION_ORIGINS` | 内置扩展 ID | 允许的固定 Chrome extension origins |
| `ALLOW_PRIVATE_NETWORK_TARGETS` | false | 是否允许可信内网 LLM/SMTP |
| `IMPORT_INBOX/PROCESSED/FAILED` | 标准 Compose 固定 | ZIP 三阶段目录 |
| `IMPORT_PROCESSED_RETENTION_DAYS` | 30，1–3650 | 成功 ZIP 自动保留天数 |
| `IMPORT_FAILED_RETENTION_DAYS` | 30，1–3650 | 失败/部分 ZIP 自动保留天数 |
| `RESTORE_STAGING` | Compose固定到`${ARCHIVE_DATA_DIR}/restores` | app流式上传与Worker读取的共享恢复暂存目录 |
| `RESTORE_FAILED_RETENTION_DAYS` | 30，1–3650 | 事实表提交前失败的恢复文件保留期；每天03:20清理 |
| `COMPONENT_RELEASE_DIR` | 自动发现 `release` | 客户端包下载目录 |
| `HOST_MONITOR_URL` | Compose 内部地址 | 容器资源采样 |
| `ARCHIVE_CGROUP_PARENT` | ai-conversation-archive | 项目 cgroup 聚合 |
| `ARCHIVE_STORAGE_BUDGET_GB` | 空 | 设置后计算项目空间百分比/告警 |
| `TZ` | Asia/Shanghai；有效IANA时区 | Cron、报告窗口、夜间runKey、Web日期边界和显示 |
| `LOG_LEVEL` | info | app/worker 日志等级 |
| `WEB_DIST` | `../web/dist` | Web 静态文件目录 |

只有应用位于可信反代后才能设置 `TRUST_PROXY`。自行重签扩展后要同步更新 `EXTENSION_ORIGINS` 并重新配对。只有可信内网 LLM/SMTP 才启用私网目标。

Host Monitor 可选：`HOST_SAMPLE_INTERVAL_MS` 默认 10000，`HOST_HISTORY_LIMIT` 默认 27。

## 4. 反向代理

公网只开放一个 HTTPS 入口，例如 `https://ai-archive.example.com:18443` → `http://127.0.0.1:18080`。不要暴露 DSM 管理端口、PostgreSQL 15432、app 内部 HTTP 或 host-monitor 9091。

`APP_ORIGIN` 必须与浏览器 Origin 的 scheme、host、port 完全一致，不能带路径、查询、用户名或密码。

## 5. 从 V2.1 升级到 V2.3

先创建 PostgreSQL 灾备和 Web 业务备份，再运行：

```sh
cd /volume1/docker/ai-conversation-archive/source
sh scripts/update-server.sh /volume1/docker/ai-conversation-archive/ai-conversation-archive-nas-V2.3.0-clean-install.tar.gz
```

脚本保留 `deploy/.env`、执行数据库备份、解压源码、构建镜像并切换源码；随后先重建 host-monitor/app，等待 migration 完成且 `/healthz` 返回目标版本，再以 `--no-deps` 启动 worker。HTTP 版本门禁是此处的最终判据；`--no-deps` 避免 Docker 在端点刚恢复时仍读到短暂滞后的容器健康状态。这样首次全文分块回填即使超过 Compose 的容器健康判定窗口，也不会因 worker 的 `service_healthy` 依赖让升级脚本误判失败。默认等待 120 分钟（`HEALTH_RETRIES=3600`、`HEALTH_SLEEP=2`），每约 60 秒记录一次等待进度；可按已验证的数据规模显式调整，但不能跳过版本健康校验。

如果默认 `BACKUP_ROOT` 对发布账号不可写，必须显式指向受控且已验证可写的备份目录；不得使用 `ALLOW_BACKUP_FAILURE=1` 绕过生产备份。`SKIP_BACKUP=1` 仅用于可丢弃测试环境。

NAS clean-install 包必须包含源码以及当前 V2.3.0 的 Chrome、Windows、macOS 三个客户端包，否则 Dockerfile 的 `COPY release release` 会失败，设备下载页也不会有完整组件。`scripts/package-nas-release.py` 会拒绝缺失客户端、混入旧版本/NAS 自身、`.env`、数据目录、构建缓存或不安全压缩路径的包。完整发布顺序为：

```powershell
pnpm package:release
```

该命令先执行发布资格检查，再依次构建 Chrome、Windows、macOS，最后生成内嵌三种客户端的 NAS 包。

`release/` 只保留当前正式版本的四个交付包、`SHA256SUMS-V2.3.0.txt` 和资格报告；旧安装包不属于当前配置基线，应在版本发布提交中删除，并通过 Git 历史按需取回。生产机同样只保留当前源码、一份最近可用的源码回滚目录、当前 NAS 包和受保留策略管理的数据库备份。

### 5.1 失败与回滚

- 镜像构建失败发生在源码切换前，现网继续使用旧 `source` 和旧容器；删除对应 `source-next-<timestamp>` 后可重新发布。
- 切换后脚本把旧源码保存在 `source-prev-<timestamp>`。健康检查失败时不要删除该目录，先收集 app/worker/migration 日志。
- 首次执行 0018 时，百万级 Message 数据可能长时间停留在 `node dist/migrate.js`，app 暂时显示 unhealthy、8080 尚未监听属于预期迁移窗口。先通过 `pg_stat_activity` 确认迁移查询仍为 active，并监控磁盘/WAL；不得因为单次健康检查失败就杀死活跃迁移。
- 0018 已按“先建表与回填 heap、后建普通/GIN 索引”编排，并限制事务内 work memory，避免百万级回填逐行维护 GIN 导致 NAS 上大量 WAL 和临时 I/O。该迁移仍是单事务；若宿主机或容器中断，应先确认 Drizzle 记录和目标表已回滚，再重新执行，不得在未确认边界时手工补记迁移。
- 数据库 Migration 为向前演进。仅回切源码不能撤销已经提交的 Schema 或数据变更；若旧代码与新 Schema 不兼容，必须在隔离环境确认后使用升级前 PostgreSQL custom-format 备份恢复。
- 回滚必须记录源版本、目标版本、备份文件、执行人、时间、失败证据和恢复后的 `/healthz`；禁止用未经验证的手工 SQL 回退事实数据。

必须让 migration runner 顺序执行全部待应用项：

- 0016 规范化旧项目名并创建视觉唯一索引；历史重复项会自动编号。
- 0017 增加 ImportJob attempt/lastRetryAt。
- 0018 回填完整正文分块、创建 GIN 索引和 Saved Search 表。
- 0019 增加 pending TOTP、Revision历史元数据兼容标记、设备/Adapter健康、邮件投递状态和 RestoreJob。
- 0020 分离 snapshot 内容身份、含标题/URL的 Revision 身份、CaptureRun payload 身份和内容完整性哈希；旧记录保持兼容/不可验证，不做伪造回填。
- 0021 增加 Restore `factsCommittedAt`、staged 文件清理标记与 `recovery_required`，保证 post-commit 异常持续维护模式。

升级后检查全文分块数量、项目重命名 warning、回收站、导入保留期、Restore共享卷、设备健康和 System Status。不要只手工执行单个 migration。

## 6. Chrome 扩展

```powershell
pnpm --filter @ai-archive/extension build
pnpm --filter @ai-archive/extension zip
```

服务器 Origin 由 `ARCHIVE_SERVER_ORIGIN` 在构建时写入；非本机必须 HTTPS。修改 Origin 或 Manifest key 会影响服务器和扩展 ID，需同步更新 `EXTENSION_ORIGINS` 并重新配对。

扩展支持 ChatGPT、Gemini、Grok、腾讯元宝、MiniMax、DeepSeek、千问和 Kimi。没有豆包 host permission、content match 或 adapter。发布前除 fixture 测试外，还要在真实登录页面验证 DOM 和虚拟列表完整扫描回退。

## 7. Windows/macOS 本地同步代理

```powershell
pnpm --filter @ai-archive/openclaw-sync build
pnpm package:windows-sync
python scripts/package-macos-sync.py
```

同步代理版本为 V2.3.0。Windows 源码入口和便携包入口都调用 `scripts/sync-local-windows-core.ps1`，避免安全/参数语义分叉；可安装当前用户隐藏计划任务，日志在 `%LOCALAPPDATA%\AIArchive\Sync\Logs`。macOS 使用 LaunchAgent，日志在 `~/Library/Logs/AIArchive`。

两端要求 Node.js 22 或 24 LTS，只读扫描 OpenClaw、Codex、Claude Code，不读取模型密钥、Cookie 或 credential。包装器默认限制 14 天、60 文件、50 MiB/文件、12,000 消息/会话、750 ms 间隔；远程必须 HTTPS，本机可 HTTP。代理对网络/5xx指数退避，429尊重Retry-After，409回退full，401停止并要求重新配对，同时回传版本/OS/扫描/同步/错误心跳。

## 8. 历史导入目录和保留期

Web 导入支持 ChatGPT、Gemini Takeout 和 Chat Memo ZIP；也可把 ZIP 放入 `${ARCHIVE_DATA_DIR}/imports/inbox`，Worker 启动和每 5 分钟扫描。

压缩上限 512 MiB；Worker 还限制路径、条目数、单条目和总展开大小。整个 ZIP 非总事务，partial 会保留成功项。Worker 每天 03:20 按两个 retention 环境变量清理 processed/failed，System Status 显示三目录占用。

## 9. LLM 与 SMTP

模型用于项目/标签整理、周报/月报和智能 Context。归档、导入、全文搜索、Revision/Diff、人工整理、基础 Context、原始导出和备份不依赖模型。

SMTP 测试会真实发信；报告邮件只含摘要和 Web 链接。LLM/SMTP 默认拒绝私网和特殊地址，并把连接固定到验证通过的 DNS 结果。

## 10. 备份与恢复

Web 业务备份在一个 `REPEATABLE READ READ ONLY` 快照中流式 gzip 导出 18 张表和设备 tokenHash；不含管理员、Session、配对码、RestoreJob、可重建全文分块和 PgBoss。高并发采集期间仍能获得跨表同一时点视图。

恢复步骤：

1. 全新部署并初始化管理员/TOTP。
2. 先用“验证备份”检查 gzip、格式、Schema、18表、引用、Delta基线、计数和主密钥指纹；此操作不写数据库。
3. 上传 gzip JSON 并取得 RestoreJob；上传由 app 流式写入 `RESTORE_STAGING`，反代不需要等待整个数据库恢复。
4. 观察 validating → validated → restoring → rebuilding-search → verifying；进入 restoring 后系统维护且不可取消。
5. 等待 completed，再检查 counts、warnings 和完整性结果。提交前 failed 可在保留期内用原 staged 文件完整重试；`recovery_required` 表示事实数据已提交且系统仍处于维护模式，点击“继续恢复后处理”只重建检索并验证完整性。
6. completed/cancelled 暂存文件立即清理；提交前 failed 默认保留30天，也可在Web删除。System Status 应显示 Restore Staging 文件数和占用。
7. 主密钥不同则重填 API Key/SMTP 密码，并核对设备 Token、会话、Revision、Message、项目、标签、报告、Saved Search 和搜索命中。

数据库灾备使用 `scripts/backup.sh`/`restore.sh`，覆盖管理员、Session、配对码和 PgBoss，不能由 Web 业务备份替代。Web恢复已任务化，但Worker仍会把受限大小的staged文件/解压JSON读入内存；生产必须为压缩≤512MiB、解压≤1GiB的最坏情况预留资源并在隔离环境演练。

## 11. 容器安全

app、worker、host-monitor 使用非 root、只读根文件系统、`no-new-privileges` 和 `cap_drop: ALL`，仅开放必要 `/tmp`、imports 和 app/worker 共享的 restore staging 可写卷。host-monitor 不挂 Docker Socket、不发布宿主端口。PostgreSQL 只保留官方 entrypoint 所需 capability。

代码依据：`deploy/docker-compose.yml`、`deploy/.env.synology.example`、`apps/server/src/config.ts`、`apps/server/src/migrate.ts`、`scripts/update-server.sh`。
