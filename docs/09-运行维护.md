## 2. 本地开发与发布前验证

```powershell
Copy-Item .env.example .env
pnpm install
docker compose -f deploy/docker-compose.yml up -d postgres
pnpm db:migrate
pnpm dev:server
pnpm dev:web
```

发布门禁：

```powershell
pnpm typecheck
pnpm test
pnpm build
docker compose -f deploy/docker-compose.yml config
pnpm release:qualify
```

`pnpm release:qualify` 汇总 typecheck/test/build；设置 `RELEASE_QUALIFICATION_E2E=true` 可加入 API E2E，`RELEASE_QUALIFICATION_REPORT=<path>` 可落 JSON 报告。`pnpm test:e2e-api` 需要正在运行且允许写入测试数据的实例，不要指向不可清理的生产库。默认期望健康版本 `V2.3.0`。

## 3. 日常检查和“需要处理”

```sh
cd /volume1/docker/ai-conversation-archive/source/deploy
docker compose --env-file .env ps
docker compose --env-file .env logs --tail=120 app worker host-monitor postgres
curl -fsS http://127.0.0.1:18080/healthz
```

正常标准：`/healthz` 为 `ok=true/version=V2.3.0`；app/postgres/host-monitor healthy；worker Up；系统状态能读取数据库、容器和存储。

每天先看 Dashboard“需要处理”：

1. 不完整会话：打开筛选，确认是否需要手动完整重采。
2. 近 24h 采集失败：查 capture 日志和设备 Token。
3. 超过 24h 未恢复：按 provider+externalSessionId 核对后续是否出现 complete CaptureRun。
4. 离线设备：确认浏览器/计划任务/LaunchAgent 是否仍在使用。
5. failed/partial 导入：查统计和源 ZIP，再决定重试。

设备页同时检查 Adapter Health 和本地代理心跳。连续失败、partial率异常、客户端版本/OS、最近扫描/同步/错误比单一 `lastSeenAt` 更适合定位静默退化。设置页定期运行归档完整性检查；错误结果不会自动改写事实档案。

Host Monitor 不可用时 API 仍返回数据库和文件指标；页面能打开不代表宿主监控健康。

## 4. 升级和 migration 核对

先做 PostgreSQL 灾备与 Web 业务备份：

```sh
cd /volume1/docker/ai-conversation-archive/source
sh scripts/update-server.sh /volume1/docker/ai-conversation-archive/ai-conversation-archive-nas-V2.3.0-clean-install.tar.gz
```

V2.3 当前 migration 到 0022。升级后核对：

- 0016：projects.normalized_name 非空且唯一；旧视觉重复是否按编号保留。
- 0017：import_jobs.attempt/last_retry_at 存在。
- 0018：conversation_search_chunks、generated search_vector、GIN index、saved_searches 和 conversations.deleted_at index 存在。
- 0019：pending TOTP、Revision captured metadata/compatibility marker、设备健康、邮件投递字段和 restore_jobs 存在。
- 0020：conversation_revisions.revision_identity_hash/content_integrity_hash 与 capture_runs.payload_identity_hash 存在；旧/已合法脱敏记录允许兼容字段为空。
- 0021：restore_jobs.facts_committed_at/staged_deleted_at、recovery_required约束和staging cleanup索引存在。
- 0022：汉字/拉丁字符边界空格的视觉重复标签组为 0；合并后的会话关系保留较高 confidence、manual 来源和 lock。
- `/healthz`、搜索、项目创建冲突、回收站、导入重试、备份验证/异步恢复均可用。

`SKIP_BACKUP=1` 只用于可丢弃环境；`ALLOW_BACKUP_FAILURE=1` 会降低升级安全性。

## 5. 队列、Cron 与 housekeeping

| 队列 | 任务 |
| --- | --- |
| `analysis-weekly` / `analysis-monthly` | 周/月报 |
| `classify-conversation` | 单会话项目/标签整理 |
| `reclassify-unlocked` | 批量整理与断点续跑 |
| `nightly-ai-maintenance` | 夜间增量整理编排 |

| `redact-storage` | 历史归档脱敏 |
| `restore-backup` | 异步业务恢复 |
| `archive-integrity` | Revision链、hash、关系和检索分块检查 |

| 时间 | 任务 | 开关/结果 |
| --- | --- | --- |
| 周一 07:30 | 周报 | `reports.weeklyEnabled`，默认 true |
| 每月 1 日 08:00 | 月报 | `reports.monthlyEnabled`，默认 true |
| 周日 06:15 | 增量整理 | `classification.autoReclassify`，默认 false |
| 每天 22:00 | 夜间整理 | `ai.nightlyMaintenanceEnabled`，默认 true |
| 每 5 分钟 | 延迟报告恢复 | 无独立开关 |
| 每 5 分钟 | Import Inbox 扫描 | Worker 启动时也扫描 |
| 每天 03:20 | housekeeping | 认证垃圾、导入 ZIP/failed Restore保留期、completed/cancelled Restore补删、30天回收站 |
| 每天 03:40 | 归档完整性检查 | 无业务开关；结果持久化到BackgroundTask |

除 Inbox Cron 外均显式使用 `TZ`。生产建议一个 Worker；多 Worker 并发尚未做压力验收。

## 6. LLM、额度和网络目标

- interactive：连接测试和智能 Context，不受 batch 固定间隔。
- batch：批量整理、周报、月报，使用全局 pacing。
- 429/Token Plan 解析 retryAt/quotaResetAt 并加缓冲；任务保存 candidate IDs 和 offset 后续跑。
- 模型故障不影响采集、全文检索、Diff、基础 Context、人工整理、导出和备份。

LLM/SMTP 默认拒绝回环、RFC1918、链路本地、云元数据和保留地址。只有可信内网服务才设置 `ALLOW_PRIVATE_NETWORK_TARGETS=true`。

## 7. 报告排错

检查：LLM 测试 → analysis_runs 状态/窗口/stats → PgBoss/worker → 周期内 complete Revision → 额度等待 → analysis 日志 → SMTP。

周报/月报查询为 `[windowStart, windowEnd)`，恰好等于右边界的 Revision 只属于下一周期。若 `boss.send()` 返回 null，run 会立即 failed、接口 503；可以重新发起，不应出现永久 queued。报告和运行列表均可分页。

SMTP 失败不应回滚已经生成的 Report；Report 本身记录 emailStatus、attempt、sentAt 和 error，Web 可重试 failed 邮件，PgBoss 与操作日志用于更深排障。

## 8. PostgreSQL 灾备与恢复

```sh
POSTGRES_USER=archive \
POSTGRES_DB=archive \
BACKUP_ROOT=/volume1/backup/ai-conversation-archive \
sh /volume1/docker/ai-conversation-archive/source/scripts/backup.sh
```

脚本生成 custom-format dump，默认保留 daily 7、weekly 4、monthly 12。

```sh
sh /volume1/docker/ai-conversation-archive/source/scripts/restore.sh \
  /volume1/backup/ai-conversation-archive/daily/archive_YYYY-MM-DD_HHMMSS.dump
```

恢复要求输入 `RESTORE`，会停止 app/worker、重建整个数据库再启动。先在隔离环境演练并核对 users、web_sessions、PgBoss、业务表和 0018 全文索引、0019可靠性字段。

## 9. Web 业务备份与恢复

- 导出 18 张业务表，不含管理员、Session、配对码、RestoreJob、全文派生分块和 PgBoss。
- 整个导出在一个 PostgreSQL repeatable-read read-only snapshot 内，跨表同一时点。
- “验证备份”只校验gzip/format/schema/18表/引用/Delta/计数/密钥指纹，不写数据库。
- gzip≤512 MiB、解压≤1 GiB；上传流式写入`RESTORE_STAGING`，Worker内部仍会把staged文件/解压JSON读入内存。
- 不同主密钥跳过加密设置。
- 正式恢复返回202和RestoreJob；阶段为validating/validated/restoring/rebuilding_search/verifying。restoring前可取消；之后维护模式且不可取消。
- 事实表事务提交前失败为 failed，退出维护模式，可在 `RESTORE_FAILED_RETENTION_DAYS` 内完整重试；源文件缺失返回410。
- 事实表提交时原子记录 `factsCommittedAt`；之后重建/验证失败为 recovery_required，继续维护模式。“继续恢复后处理”只重建全文索引并验证完整性，成功才 completed。
- completed/cancelled文件立即删除；pre-commit failed默认保留30天，支持Web手动删除并由03:20 housekeeping清理过期文件。

只有completed才表示业务替换、全文重建和归档完整性检查全部完成。恢复后核对counts、实体计数、全文命中、Saved Search、设备Token、warnings与integrity；recovery_required 时不要绕过维护模式开放业务流量。Web备份不能替代数据库灾备。

## 10. 导入排错与磁盘治理

任务不动时检查 worker、PgBoss `import-archive`、ZIP 格式/大小、目录 UID 1000 权限、ImportJob status/stats/error/attempt 和源文件位置。

failed/partial 重试规则：

- UI 手动重试会把 failed ZIP 移回 inbox；文件不存在返回 409。
- 重新上传同 SHA-256 ZIP 会复用原 ImportJob 重新入队。
- 入队 null 立即返回 503 并恢复 failed 状态。
- ZIP 非总事务；partial 的 imported/unchanged 不回滚，重试依赖 snapshotHash 幂等补齐。

System Status 应显示 Inbox/Processed/Failed 和 Restore Staging 的 files/bytes，并把后者计入项目存储预算。默认 processed/failed ZIP 与 pre-commit failed Restore 各保留30天，可配置1–3650天；页面可清理导入文件，也可逐项删除失败恢复文件。

## 11. 采集与全文检索排错

- Chrome 无采集：确认属于 8 个平台、站点权限、Session ID、配对和 capture 日志。豆包无 adapter。
- 增量 409：客户端应完整重采。
- 虚拟列表找不到末消息：V2.3 应回退 full scan；若仍无记录，查 DOM adapter 日志，不应接受静默 skip。
- 不完整：核对 top/bottom/stable/completenessReason，滚动加载完整后手动重采。
- 401：设备撤销或 Token 失效；Chrome应保留Outbox并显示AUTH_REVOKED，本地代理应停止重试；重新配对后再继续。
- 搜索不到：先确认 migration 0018 和 search chunks；从“设置 → 系统状态”重建并核对 chunkCount。
- 搜索 `%`/`_`：V2.3 应按字面；若出现广泛命中，查 `literalContainsPattern`。

全文分块是派生表，可重建；不要把删除分块当作删除原始归档。英文等文本使用 GIN `simple` tsvector，中文连续文本主要依赖 ILIKE 字面回退。用 `pnpm --filter @ai-archive/server benchmark:search` 在目标规模数据上记录P50/P95/P99与EXPLAIN JSON；脚本不会自动构造百万级样本。

## 12. 项目、标签、Diff 与回收站排错

- 项目重复：检查 `normalized_name`；API 应返回 409，纯空格应 400。
- 项目残留建议：人工分配/释放后 `suggestedName` 应为 null。
- 时间线少：检查 total/offset/hasMore 和 Web Pagination，不应固定 100。
- Context 智能版失败：选仅历史索引或接受基础版 fallback。
- 标签“交还 AI 管理”：关系应变为 source=auto、locked=false、confidence=null。
- Tag 合并：应在事务内锁 source/target 后读取关系；并发测试还需数据库环境验收。
- Revision Diff：V2.3新Revision可比较历史标题/URL；Migration前元数据标为不可验证，不应误判为无变化。
- 回收站：普通 DELETE 写 deleted_at；永久接口只接受已删除记录和精确 `DELETE`；Worker 每天清理 30 天前记录。

## 13. 认证与 Session 排错

- `/auth/me` 401 才代表登录失效；网络错误和 5xx 应在 Web 显示独立错误。
- 改密/发起TOTP重绑必须同时验证当前密码和当前TOTP；reset只生成约10分钟pending Secret。
- 用新验证器验证码调用confirm后旧密钥才失效；响应丢失前旧密钥不会被提前替换，pending也可取消。
- 每天 03:20 清理过期 Session/Pairing Code；鉴权本身不依赖物理清理。
- Session 页面可注销其他浏览器；注销当前 Session 后 Cookie 被清除。

丢失凭据时必须拥有服务器Shell、正确`DATABASE_URL`和`APP_MASTER_KEY`。在app容器或源码环境运行：

```sh
AI_ARCHIVE_RECOVERY_PASSWORD='至少12字符的新密码' node dist/admin-recovery.js reset-password
node dist/admin-recovery.js reset-totp
node dist/admin-recovery.js revoke-sessions
```

reset-password/reset-totp会注销全部Web Session；reset-totp会在当前终端显示新Secret和OTP URI，应避免Shell历史/日志泄漏并立即保存。源码开发可用`pnpm --filter @ai-archive/server admin:recovery -- <command>`。

## 14. 监控和日志边界

- Dashboard 不自动轮询；Token 为来源上报和估算混合值，不是账单。
- Activity 是分页聚合视图；采集异常聚合只代表近 24 小时的最新异常摘要，完整细节看 logs/capture_runs。
- 日志支持offset、1h/24h/7d/30d和自定义日期；日期按实例`TZ`解释，结束日右开。
- “最近 Web 备份”日志只能证明服务器开始导出；使用Backup Verify并在隔离环境演练，才能提高可恢复置信度。
- Host Monitor 依赖 Linux `/proc` 和 cgroup；非 Linux 开发环境可缺指标。

## 15. 安全检查

1. 随机 32 字节 Base64 `APP_MASTER_KEY` 已离线备份。
2. 生产 `APP_ORIGIN` 是真实 HTTPS Origin，Cookie Secure。
3. PostgreSQL、DSM、内部 HTTP、host-monitor 不暴露公网。
4. `TRUST_PROXY` 和 `EXTENSION_ORIGINS` 只包含真实可信对象。
5. 默认保持 `ALLOW_PRIVATE_NETWORK_TARGETS=false`。
6. app/worker/host-monitor 非 root、只读、no-new-privileges、drop ALL。
7. imports 与 restores 目录只给 UID 1000 必要权限；导入/恢复保留期符合磁盘预算。
8. 定期注销不用的 Session、撤销设备、轮换外部密钥。
9. 历史脱敏和永久删除前有可恢复数据库备份。
10. 发布前执行依赖、镜像、Secret、真实站点、SMTP/LLM 和恢复演练。

## 16. 发布一致性

根包、server、Web、Chrome manifest、contracts、同步代理、e2e期望版本和文档当前均为V2.3.0。包名、manifest/package version、变更历史和设备组件发现结果必须与实际产物一致。Windows源码/便携入口必须共同调用`sync-local-windows-core.ps1`。

发布包不得包含 `node_modules`、`.env`、数据库、导入临时文件、本地日志、浏览器状态或旧 release 目录。变更历史只追加真实事实，不反向改写旧版本。

代码依据：`apps/server/src/worker.ts`、`jobs/import-job.ts`、`services/analysis.ts`、`backup.ts`、`restore.ts`、`archive-integrity.ts`、`search-chunks.ts`、`services/auth.ts`、`admin-recovery.ts`，`scripts/backup.sh`、`restore.sh`、`update-server.sh`、`release-qualification.mjs`。
