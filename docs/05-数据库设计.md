## 1. 模型原则

Conversation、累计 Revision、Message、Message Segment 及 Revision 的差异采集证据是不可被分类结果替代的归档事实来源。每个会话保留一份持续更新的正文，采集窗口缺少旧消息时不会据此删除旧内容。Project、Tag 和 Saved Search 是可修改组织数据；Report 是持久化周期输出；Project Context 在请求时生成，不落库；Conversation Search Chunk 是可重建的派生全文索引。

系统当前有 23 张应用表。没有 role、tenant、subscription、knowledge item、notification、webhook 或独立回收站表；回收站使用 `conversations.deletedAt`。Web 业务备份仍只导出其中18张可移植业务表。

## 2. 关系概览

```text
users 1 ── * web_sessions

devices 1 ── * conversation_revisions
devices 1 ── * capture_runs
pairing_codes ──领取──> devices（无外键，领取后写 claimedAt）

conversations 1 ── 1 conversation_revisions（canonical snapshot）1 ── * messages 1 ── * message_segments
conversation_revisions/messages 1 ── * conversation_search_chunks（派生索引）
conversations 1 ── 0..1 conversation_projects * ── 1 projects
conversations * ── * tags（经 conversation_tags）

projects 1 ── * reports（删除项目时 report.projectId 置空）
analysis_runs / background_tasks / import_jobs / restore_jobs / capture_runs / operation_logs 保存运行记录
settings / redaction_rules / saved_searches 保存全局配置、规则和常用视图
```

设备不直接挂在 Conversation 上。来源设备记录在 Revision 和 CaptureRun；Conversation 的展示来源由 Revision 的设备 kind、Provider 和 captureMode 推导。

Migration 0023 在 `conversations` 增加可空 `parent_external_session_id`，通过 `(provider, external_session_id)` 定位父会话，允许父记录晚于子记录到达。父子关系不修改消息和 Revision 身份；数据库禁止自身作为父会话，采集事务拒绝循环关系。`(provider, parent_external_session_id)` 索引用于子记录查询。Web 备份按表字段导出并保留该关系；旧备份缺失字段时按空关系兼容。

历史关系回填只更新已有 Codex 会话的父 ID，不创建未归档会话，不修改消息、Revision 或 `deletedAt`；重复相同关系保持幂等。主入口查询与项目/首页会话数读取这一组织关系，原始归档身份不变。V2.4.0 的累计只发生在同一 `provider + externalSessionId` 内；父会话与子代理各有自己的正文，不跨会话拼接。

## 3. 身份与设备

### 3.1 `users`

字段：`id`、`singletonKey`、`username`、`passwordHash`、`totpSecretEncrypted`、`pendingTotpSecretEncrypted`、`pendingTotpExpiresAt`、`createdAt`。`singletonKey=1` 且唯一，因此只允许一个管理员。active/pending TOTP Secret 都使用 `APP_MASTER_KEY` 加密；只有新码确认成功才把 pending 原子提升为 active。

### 3.2 `web_sessions`

字段：`id`、唯一 `tokenHash`、`userId`、`expiresAt`、`createdAt`。删除用户级联删除 Session。退出、远程注销和每天 housekeeping 都会删除记录；过期 Session 即使尚未清理也无法通过鉴权。

### 3.3 `devices`

字段：`id`、`name`、`kind`、唯一 `tokenHash`、`lastSeenAt`、`revokedAt`、`clientVersion`、`os`、`lastScanAt`、`lastSuccessfulSyncAt`、`lastErrorAt`、`lastErrorCode`、`trackedFiles`、`skippedFiles`、`createdAt`。kind 为 `chrome_extension`、`openclaw_sync`、`importer`；Web 只创建前两类。撤销写 `revokedAt`，再次删除才物理删除；Revision/CaptureRun 的设备外键置空。

### 3.4 `pairing_codes`

字段：`id`、唯一 `codeHash`、`requestedName`、`requestedKind`、`expiresAt`、`claimedAt`、`createdAt`。领取通过事务和 advisory lock 保证一次性；每天 housekeeping 删除已过期或已领取的历史记录。

## 4. 核心归档与检索

### 4.1 `conversations`

| 字段 | 说明 |
| --- | --- |
| `id` | UUID 主键 |
| `provider` | 12 个 Provider 枚举之一 |
| `externalSessionId` | 外部稳定 Session ID |
| `parentExternalSessionId` | 可空父会话 Session ID；按同一 provider 解析 |
| `title` / `canonicalUrl` | 可空标题和原链接 |
| `updatedAt` / `createdAt` | 排序和审计时间 |
| `deletedAt` | null 为活跃；非 null 为进入回收站的时间 |

`provider + externalSessionId` 唯一。普通删除只写 `deletedAt`；恢复置 null；确认永久删除或 30 天到期清理才级联移除 Revision、消息、项目/标签关系和检索分块。

### 4.2 `conversation_revisions`

V2.4.0 沿用表名，但它承载当前累计档案。归并后的会话只有一个 `isAccumulated=true` 的 canonical 行；该行 `id` 固定，后续采集在会话级锁和事务内更新正文及元数据，不生成供用户选择的历史版本。Migration 0024 的部分唯一索引 `conversation_accumulated_revision_uidx` 保证每会话最多一个 canonical；升级归并还会删除其余旧 Revision，使物理存储保持一份。

关键字段：

- 当前身份：`id`、`conversationId`、`isAccumulated`、`branchFingerprint`、`snapshotHash`、可空兼容字段 `revisionIdentityHash`。`snapshotHash` 覆盖已脱敏消息和完整性，Revision identity 再包含标题/canonical URL；`conversationId + revisionIdentityHash` 唯一。两种身份忽略 capturedAt，用于内容/元数据变化识别，标题或 URL 变化更新同一行。
- 可验证性：`contentIntegrityHash` 覆盖当前可重建正文、消息元数据及相关采集元数据；canonical 校验还包含累计 Token 和 `mergeEvidence`。它用于完整性检查，也作为增量比较并更新（CAS）的内容基线。归并后按实际累计内容重算；尚未归并的旧兼容行可为空，完整性检查会单独计入不可验证数量。
- 采集证据：`mergeEvidence={variants,warnings}`。`variants` 保存同一消息 ID 的不同正文等需要保留的差异片段，不保存整份会话历史快照；`warnings` 保存类型和相关 `messageIds`，标示无法确定的顺序或分支关系。可验证的精确前缀扩展可以由更长正文覆盖旧观察，不能确定的异文仍保留。差异片段不重复计入主正文 `messageCount`，也不作为确定连续问答展示。
- 完整性：`completeness`、`topReached`、`bottomReached`、`stable`、`completenessReason`。
- 采集方式与存储：`captureMode`、`triggerReason`、`baseRevisionId`、`baseMessageCount`、`storageKind`。canonical 始终为物理 `snapshot`，两个 base 字段为空；请求可以是 append，但落库不新建 delta 链。
- 最近采集元数据：`adapterVersion`、`sourceDeviceId`、`capturedAt`、`capturedTitle`、`capturedCanonicalUrl`、`metadataCaptured`。
- 统计：`messageCount`、列表展示计数 `presentationMessageCount` / `storedMessageCount` / `sourceContentPending`、正文/推理/工具文本单位、6 类可空来源 Token 字段。`searchText` 从 Migration 0027 起只保留空字符串以兼容 v1 备份，采集不再构造或维护它，旧 trigram 索引已删除。

`baseRevisionId` 未声明数据库外键，保留是为了还原旧 delta 数据。升级先按旧链物化全部快照，再累计合并、保留差异证据，最后删除冗余 Revision 和消息副本；不会在还原前删除基线。已有 canonical 优先保留其 ID，否则选定一条旧行作为固定 ID。重复归并不再重写已完成的档案，归并本身不创建 CaptureRun，也不修改会话删除状态。

全量导出和分析使用 `loadCurrentConversationArchive()`；Web 详情使用 `loadCurrentConversationPage()`，先选择消息页，再读取该页正文。两者均在 `REPEATABLE READ READ ONLY` 事务中取得可变元数据与正文。canonical 优先于迁移期间的旧 complete/partial 行，避免一次响应混入更新前计数和更新后正文。

Migration 0027 增加三份可重建派生数据：`conversation_revision_presentation` 保存已核对当前正文的顺序与物理消息/差异正文引用；`conversation_revision_observations` 保存 inactive/resolved/unresolved 历史观察的引用；`conversation_summaries` 每会话保存当前修订累计文本量、消息数、Token 与最近活动时间。引用表不复制正文；替代正文可同时保留物理消息位置与 variant 下标，从而保留搜索锚点和原消息元数据。采集在同一事务内更新计数和引用；数据库触发器随修订增删改及会话活动更新汇总。首页文本统计只聚合汇总表，组织统计在 SQL 内计数，7 日增长使用最近活动时间。

三份派生表不进入 v1 业务备份。恢复保留旧 `searchText` 字段兼容，但将其置空，并清空派生计数后逐修订回填；迁移执行器和恢复后处理均调用可恢复的 `backfillArchiveReadModels()`，每次只加载一个修订。部分索引 `(id) WHERE presentation_message_count IS NULL` 避免回填反复扫描已处理记录。列表新增活跃会话 `(updated_at DESC, id DESC)` 部分索引、标题 trigram 索引及当前修订复合索引；筛选在 SQL 内用 EXISTS / JOIN，子会话数仅对当前结果页聚合。

### 4.3 `messages` 与 `message_segments`

Message 字段：`id`、`revisionId`、`externalMessageId`、`ordinal`、`role`、`model`、`sourceCreatedAt`、`createdAt`；`revisionId + ordinal` 唯一。role 为 user、assistant、system、tool、unknown。

Segment 字段：`id`、`messageId`、`ordinal`、`type`、`content`、`href`、`language`、`createdAt`；`messageId + ordinal` 唯一。type 为 text、reasoning、code、citation、tool_status。

稳定 `externalMessageId` 在累计主正文中只出现一次，新增片段不能覆盖掉窗口外旧消息。排序调整或更丰富正文导致重建时，按消息身份尽量复用已有 `messages.id`，并保留能够匹配到的最早 `createdAt`；`sourceCreatedAt` 仍表示来源消息时间。无法匹配的消息才分配新行身份，不承诺缺失来源 ID 的旧数据一定可精确对应。

正常追加若旧消息序列是新正文的严格、完全相同前缀，且差异证据未变、没有需要迁移的差异索引，服务端只插入新增 Message/Segment/SearchChunk，并更新 canonical 元数据。旧消息、段落与索引不会因每次尾部追加而整篇删除重写；重排、正文更新或差异证据变化时才走需要重建的路径。

### 4.4 `conversation_search_chunks`

字段：`id`、`revisionId`、`messageId`、`chunkIndex`、`content`、`createdAt`，数据库另有 generated `search_vector`。`messageId + chunkIndex` 唯一，`search_vector` 建 GIN 索引。当前按每条消息合并正文后每 4,000 字符切块。

该表不属于事实源，也不进入 Web 业务备份；采集时写入，恢复或管理员调用 rebuild 时从 Message/Segment 与 `mergeEvidence.variants` 全量重建。差异内容按消息 ID 归到主消息，无法定位时归到首条消息索引，因此保留的异文也可搜索。

### 4.5 `capture_runs`

每次采集保留轻量运行记录，不重复存一份会话正文。字段包括设备、Provider、Session、adapterVersion、messageCount、idempotency key、snapshotHash、payloadIdentityHash、模式、触发原因、增量基线、状态、错误、捕获/创建时间；Migration 0024 新增 `requestHash` 和 JSON `receipt`。

`deviceId + idempotencyKey` 唯一。新请求以 `requestHash` 校验规范化后的完整 payload：同 key 不同请求拒绝，同 key 相同请求先返回已接受 receipt 并标记 `unchanged=true`，即使此时累计正文的增量基线已经前进，也不再次追加消息或累计 Token。无新字段的旧记录仍按 `payloadIdentityHash`/`snapshotHash` 兼容核对；无法安全重放的旧 delta 要求重新完整采集。

receipt 保存 `conversationId`、固定 `revisionId`、`unchanged`、本次完整性/消息数、`archiveMessageCount`、`archiveCompleteness`、采集方式和触发原因。只有本次完整采集与累计档案一致并满足完整性要求时，才返回 `baselineContentHash`。append 必须带当前 `baseContentHash`，同时验证 branch、可选 Revision ID、基线消息数和末消息身份/指纹；旧 hash 或缺失 hash 返回 409，客户端改做完整采集。固定 Revision ID 本身不能充当内容未改变的证据。

历史 CaptureRun 随归并保留；其中旧 revision/base 标识属于采集审计信息，不再代表必须保留的正文版本链。状态为 complete、partial、failed；adapterVersion/messageCount 支撑 Adapter Health。

## 5. 项目、标签与常用视图

### 5.1 `projects`

字段：`id`、`name`、唯一 `normalizedName`、`description`、`archived`、`updatedAt`、`createdAt`。`name` 保存 NFKC、trim、连续空白折叠后的显示值；`normalizedName` 再大小写折叠用于视觉唯一性。

### 5.2 `conversation_projects`

字段：`conversationId` 主键、可空 `projectId`、`confidence`、`lockedByUser`、`suggestedName`、`updatedAt`。一条 Conversation 最多一个主项目。人工分配、释放或合并时会清理不再适用的 `suggestedName`。

### 5.3 `tags` 与 `conversation_tags`

Tag 保存 `name`、唯一 `normalizedName`、时间戳，使用与项目相同的 NFKC、空白和大小写规范化思路。

关系表以 conversationId/tagId 为复合主键，另有 `confidence`、`source=auto|manual`、`lockedByUser` 和时间戳。人工添加为 manual+locked；“交还 AI 管理”转换为 auto+unlocked，并清空人工 confidence。

### 5.4 `saved_searches`

字段：`id`、`name`、唯一 `normalizedName`、JSON `query`、`updatedAt`、`createdAt`。query 只保存会话列表允许的字符串筛选参数，不保存分页 offset；名称按规范化值唯一。

## 6. 报告、任务、导入与日志

### 6.1 `analysis_runs`

kind 为 weekly、monthly、manual；status 为 queued、running、completed、failed。保存半开周期 `windowStart/windowEnd`、错误、JSON stats、完成和更新时间。`kind + windowStart + windowEnd` 唯一。报告入队 null 会立即从 queued 改 failed。

### 6.2 `background_tasks`

kind 为 `classification_rebuild`、`storage_redaction` 或 `archive_integrity`；status 为 queued、running、completed、failed。保存 total/processed/succeeded/failed 计数、message、error、JSON stats 和时间。

### 6.3 `reports`

字段：`id`、`kind`、可空 `projectId`、`periodStart`、`periodEnd`、`title`、`summary`、`bodyMarkdown`、`emailStatus`、`emailAttempts`、`emailSentAt`、`emailError`、`createdAt`。`kind + periodStart + periodEnd` 唯一；邮件状态为 queued/sent/failed/not_configured。

### 6.4 `import_jobs`

字段：`id`、`filename`、唯一 `fileHash`、可空 `provider`、`status`、`attempt`、`lastRetryAt`、JSON `stats`、`error`、完成/更新/创建时间。

status 为 queued、processing、completed、partial、failed。相同 hash 的 failed/partial 重试复用同一行；`attempt` 递增并更新 `lastRetryAt`。partial 的 stats 记录 imported、unchanged、failed、total。

### 6.5 `restore_jobs`

保存上传文件名和仅服务端可见 stagedPath、status、progress、phaseMessage、counts、warnings、error、started/completed/updated/createdAt，以及 `factsCommittedAt`、`stagedDeletedAt`。状态为 queued、validating、validated、restoring、rebuilding_search、verifying、recovery_required、completed、failed、cancelled。事实表事务提交时原子写 `factsCommittedAt`；post-commit 后处理失败进入 recovery_required 并保持维护模式。stagedDeletedAt 防止清理与重试竞态。该表是本实例运维状态，不进入18表Web业务备份，恢复业务表时保留。

### 6.6 `operation_logs`

保存 scope、level、message、status、entityType/entityId、JSON metadata 和 createdAt。scope 为 analysis、capture、classification、device、import、system；level 为 info、warning、error。

## 7. 全局配置与脱敏

`settings` 是 key/value 表，另有 `encrypted` 和 `updatedAt`；`llm.apiKey`、`smtp.password` 加密。`redaction_rules` 保存 pattern、replacement、enabled、createdAt。TOTP Secret 单独保存在 users。

## 9. Web 业务备份映射

18 个导出键为：

`devices`、`conversations`、`conversationRevisions`、`messages`、`messageSegments`、`captureRuns`、`projects`、`conversationProjects`、`tags`、`conversationTags`、`analysisRuns`、`backgroundTasks`、`reports`、`savedSearches`、`settings`、`redactionRules`、`importJobs`、`operationLogs`。

不包含 users、webSessions、pairingCodes、conversationSearchChunks、restoreJobs 和 PgBoss 内部表。当前备份保留累计正文、`isAccumulated`、`mergeEvidence` 及 CaptureRun 的请求身份/回执；不把差异内容丢弃或重新展开为会话版本。旧备份缺失新字段时按 legacy 行和空证据兼容，还原其旧 delta 链后按相同累计规则归并，再重建全文分块并执行完整性检查。恢复后处理重试也先完成归并；该阶段失败继续保持维护模式，不能仅因事实表提交就开放服务。旧备份的 knowledge 数据会忽略并 warning，旧项目名在恢复准备阶段规范化并解决视觉重复。

设备 tokenHash 属于备份，因此恢复后是否重配取决于客户端明文 Token、服务地址和恢复出的设备记录是否匹配。

## 10. 状态与删除语义

| 实体 | 状态/变化 | 删除/保留规则 |
| --- | --- | --- |
| Web 实例 | uninitialized → initialized | 只能初始化一次 |
| TOTP | active + pending → active(new)，或 pending cancelled/expired | 确认前旧Secret不失效 |
| Session | active → expired/deleted | logout/远程注销/每日 housekeeping 删除 |
| Device | active → revoked → deleted | 撤销不可恢复；删除后 Revision 来源置空 |
| Conversation | active → trashed → active/deleted | 30 天可恢复；确认或到期永久删除 |
| Revision | 当前 canonical snapshot；complete/partial | 同一行持续更新；升级还原并合并旧 snapshot/delta；随 Conversation 永久删除级联 |
| Project | active ↔ archived；source → merged/deleted | 归档可恢复；合并删除源项目 |
| Tag relation | manual+locked → auto+unlocked，或 deleted | 交还 AI 后可被自动调整 |
| Analysis/Task | queued → running → completed/failed | 持久记录，无 UI 删除 |
| Import | queued → processing → completed/partial/failed | partial/failed 可回到 queued 重试 |
| Restore | queued → validating → validated → restoring → rebuilding_search → verifying → completed；pre-commit→failed；post-commit→recovery_required | restoring前可取消；failed完整重试；recovery_required仅重建/验证并持续维护模式 |
| 导入文件 | inbox → processed/failed → deleted | 按配置保留期或 UI 立即清理 |
| Restore staged文件 | uploaded → completed/cancelled立即删除；pre-commit failed保留→expired/manual deleted | 默认30天；`stagedDeletedAt`记录不可再重试 |

## 11. 归并后的空间回收

删除冗余 Revision/消息会产生 PostgreSQL 死元组，逻辑条数减少不等于数据文件立即缩小。普通 `VACUUM` 主要把空间交还同表后续写入复用，通常可与正常读写并行；表尾空页在满足条件时也可能截断。`VACUUM FULL` 重写表和索引以回收物理文件空间，需要额外临时磁盘空间，并在处理期间持有 `ACCESS EXCLUSIVE` 锁，阻塞该表的读写；应安排维护窗口，不作为每次采集或归并的自动步骤。参见 [PostgreSQL 16 VACUUM](https://www.postgresql.org/docs/16/sql-vacuum.html)。

代码依据：`apps/server/src/schema.ts`，migration 0000–0024，`apps/server/src/services/capture.ts`、`conversation-accumulation.ts`、`conversation-merge.ts`、`revision-storage.ts`、`backup.ts`、`restore.ts`、`archive-integrity.ts`、`search-chunks.ts`。

## V2.4.7 正文搜索索引

Migration `0026_search_content_trigram.sql` 使用已启用的 pg_trgm，为 `conversation_search_chunks.content` 建立 `conversation_search_chunks_content_trgm_idx` GIN 索引。它与原 `search_vector` GIN 支持正文包含/全文条件的 BitmapOr；频繁短词仍可能由优化器选择顺序扫描。首次建立需要磁盘与写入维护窗口，迁移仅设置事务内 maintenance_work_mem，不改变正文或搜索结果语义。分页摘要按结果页批量查询并保留会话、修订、消息位置的对应关系。


## 会话搜索与项目汇总（Migration 0028–0030）

`conversation_search_documents` 每会话仅保存词条就绪标记。Migration 0029 把旧短词摘要拆为 `conversation_search_terms(term, conversation_id)`，主键按 term、conversation_id 排列，使用 C 排序规则精确等值比较；conversation_id 辅助 B-tree 支持维护与级联删除。Migration 0030 移除 content 全文副本，不重建已经就绪的词条。

纯中文单字、双字直接读取词条对应会话；长短语先求全部相邻双字的会话交集，再仅对候选会话的各修订检查实际分块，首个命中即停。MATERIALIZED 候选与 LATERAL 限制核对范围，分块间不拼接成短语；保留标题、历史修订和父会话扩展语义。英文、混合与操作符仍走既有分块 GIN。

追加采集仅从新增消息写入的实际分块提取词条，并插入缺失关系；不构建全文副本，不把全部已有词条传回数据库。元数据更新跳过搜索写入。正文改写、重排、修订合并时采用完整词条校准，避免删除仍在其他消息中存在的词条。一般归档加载、哈希及合并仍有原有成本，不能把搜索写入优化理解为采集全流程已经变成常数时间。

新装、恢复和脱敏重建均从真实分块提取词条，按 `(revision_id,id)` 索引每256块分页；只在内存保留去重词条集，不拼接全文。就绪标记行锁与同一事务保护恢复基线，缺失基线的追加操作会先完整恢复。搜索元数据、分块、词条均为派生数据，不计入业务 JSON 备份。

搜索计数与分页共用一个 MATERIALIZED 命中集。只为当前页的修订读取摘要，先按 revision_id 读取分块，首个匹配后读取对应消息位置并停止；摘要不承诺最小消息序号，避免为此扫描完整修订，不从全局 GIN 开始。

`project_conversation_rollups` 维护来源会话到可见主会话的项目关系和活动时间。数据库触发器覆盖分组、父关系、父会话晚到、软删除/恢复、永久删除和修订活动；项目归档在读取时过滤。七日增长按实际 activity_at 动态过滤，不缓存会过期的七日计数。首页只聚合较小的汇总关系，返回总数和最近12个有增长的项目；标签只查询这12个项目。迁移和事务回滚测试覆盖这些生命周期。

V2.4.12 的长中文短语在候选修订约束内采用字面 LIKE，允许 PostgreSQL 组合既有正文 trigram 与修订索引，首个命中即停；摘要复用相同核对逻辑。单字、双字不走这条正文 trigram 路径。
