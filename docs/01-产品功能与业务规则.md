# 1. 项目概述

知言归藏是面向个人或小型自托管场景的 AI 会话归档系统。它解决的不是“再做一个聊天客户端”，而是把分散在网页 AI、OpenClaw、Codex、Claude Code 和官方导出包里的会话，转成可追溯的 Conversation → Revision → Message → Segment 版本化档案，再提供搜索、项目/标签整理、时间线、导出、报告、备份和运行监控。

主要使用者和系统参与者如下：

- **归档管理员**：唯一 Web 用户，负责查看、整理、导入、导出、删除、配置和运维；系统没有多用户、团队、套餐或细粒度 RBAC。证据：`apps/server/src/schema.ts:28`（`users.singletonKey` 唯一）、`apps/server/src/services/auth.ts:41`（`bootstrapAdmin`）。**已确认**。
- **Chrome 采集设备**：在支持的网站页面中自动/手动采集，离线时进入 IndexedDB 发件箱，使用设备 Bearer Token 上传。证据：`apps/extension/entrypoints/content.ts:251`（内容脚本主流程）、`apps/extension/entrypoints/background.ts:122`（`flushOutbox`）。**已确认**。
- **本地同步设备**：扫描 OpenClaw、Codex、Claude Code JSONL，监听文件变化并上传全量或增量快照。证据：`apps/openclaw-sync/src/index.ts:899`（`transcriptFiles`）、`:978`（`run`）。**已确认**。
- **后台 Worker**：处理导入、AI 整理、报告、邮件和历史脱敏，并运行定时任务。证据：`apps/server/src/worker.ts:60-223`。**已确认**。
- **`importer` 设备类型**：协议和服务端配对接口允许这种 kind，但 Web 配对表单没有入口，仓库也没有发现独立 importer 设备客户端；任意已配对 kind 实际都能调用统一采集接口。证据：`packages/contracts/src/index.ts:120-126`（`DeviceKindSchema`）、`apps/server/src/routes/captures.ts:15`。**已确认（后端能力）/待确认（产品客户端）**。

技术形态是 React 单页 Web、WXT/Manifest V3 Chrome 扩展、Node.js/Fastify API、Node.js 本地同步 CLI、PostgreSQL 17 与 PgBoss Worker；Compose 还包含只读 Host Monitor。证据：`apps/web/src/App.tsx:3589`、`apps/extension/wxt.config.ts:34-68`、`apps/server/src/app.ts:37`、`deploy/docker-compose.yml:1-149`。

产品事实来源是原始归档，不是 AI 派生结果：会话可有多个 Revision，一个 Revision 可是完整快照或只保存新增消息的 Delta；读取时重建逻辑链。项目、标签、报告属于可重建或可人工修正的组织层。证据：`apps/server/src/schema.ts:71-200`、`apps/server/src/services/revision-storage.ts:21-99`。

## 4.1 身份、认证与 HTTP 安全

### 4.1.1 首次初始化管理员

- **功能名称/模块/目的**：首次初始化管理员；身份与访问；为一个空实例建立唯一控制账号。
- **使用者/入口/触发**：未初始化访问者；登录页“初始化”表单；`POST /api/v1/auth/bootstrap`。
- **前置条件/正常流程**：数据库没有 `users` → 提交用户名和密码 → 服务端生成 TOTP Secret、加密保存 → 返回 Secret 与 `otpauth` URI，用户之后用 TOTP 登录。
- **输入字段/校验**：用户名 3–64 字符；密码 12–256 字符；浏览器表单也使用相同最小长度；接口 3 次/15 分钟。
- **输出/业务规则/权限**：201 返回 TOTP 信息；`singleton_key=1` 唯一约束保证只存在一个管理员；没有创建第二用户入口。
- **状态变化**：实例 `initialized=false → true`；用户记录创建，但不会自动创建 Web Session。
- **异常/边界**：重复或并发初始化返回 409；Zod 校验保持 400，数据库/内部故障不再伪装为 409，而是进入统一 500 处理。
- **配置/第三方**：TOTP 不依赖外部服务；Secret 使用 `APP_MASTER_KEY` 加密；密码使用 Argon2id。
- **实体/代码**：`users`；`apps/server/src/routes/auth.ts:28-44`（`authRoutes`）、`apps/server/src/services/auth.ts:41-63`（`bootstrapAdmin`）、`apps/server/src/schema.ts:28-35`。
- **实现状态/可信度**：已实现，**已确认**；E2E 覆盖初始化与登录（`scripts/e2e-api.mjs:54-95`）。

### 4.1.2 登录与建立会话

- **功能名称/模块/目的**：管理员登录；身份与访问；用三因素中的用户名、密码、动态码建立 30 天 Web 会话。
- **使用者/入口/触发**：管理员；登录页；`POST /api/v1/auth/login`。
- **前置条件/正常流程**：实例已初始化 → 校验用户名/密码 → 解密 TOTP Secret 并验证 6 位码 → 创建随机 Session Token，仅把哈希写库 → 设置 Cookie。
- **输入字段/校验**：用户名 1–64、密码 1–256、TOTP 必须正好 6 位数字；5 次/5 分钟；Web 页面把密码/TOTP设为必填。
- **输出/业务规则/权限**：200 返回用户；Cookie `archive_session` 为 HttpOnly、SameSite=Strict，生产为 Secure；服务器只接受未过期 Session。
- **状态变化**：新增 `web_sessions`，过期时间当前时刻 +30 天；登录不会撤销旧会话。
- **异常/边界**：用户名、密码、TOTP 任一错误均为 401，避免透露具体失败因素；系统没有忘记密码邮件或第二管理员，但已提供登录后账号管理和仅限服务器 Shell 的恢复 CLI。
- **配置/第三方**：`COOKIE_SECURE`，生产环境强制 Secure；反向代理行为受 `TRUST_PROXY` 影响。
- **实体/代码**：`users`、`web_sessions`；`apps/server/src/routes/auth.ts:46-65`、`apps/server/src/services/auth.ts:66-118`。
- **实现状态/可信度**：已实现，**已确认**。

### 4.1.3 查询登录状态、当前用户与退出

- **功能名称/模块/目的**：状态查询、当前用户、退出；供 SPA 决定显示登录页或主界面，并结束当前会话。
- **使用者/入口/触发**：任意访问者可 GET `/auth/status`；登录用户通过 App 启动调用 `/auth/me`；侧栏退出调用 `POST /auth/logout`。
- **前置条件/流程**：`me` 和 `logout` 需有效 Cookie；退出删除当前 Token 哈希对应的一条 Session，并清 Cookie。
- **输入/校验/输出**：无业务输入；status 返回 `{initialized}`；me 返回 `{user}`；logout 返回 204。
- **规则/权限/状态**：普通退出只结束当前浏览器；管理员也可在账号安全页注销其他 Session。
- **异常/边界**：Web 只把 401 解释为登录失效；网络异常和 5xx 分别显示连接/服务端错误并允许重试。Worker 每天 03:20 清理过期 Session 和无效配对码，鉴权仍会即时拒绝尚未物理清理的过期记录。
- **配置/第三方**：无。
- **实体/接口/代码**：`web_sessions`；`apps/server/src/routes/auth.ts:28,67-80`、`apps/server/src/services/auth.ts:121-129`、`apps/web/src/App.tsx:3587-3589`。
- **实现状态/可信度**：主流程与 housekeeping 已实现，**已确认**。

### 4.1.4 同源、CORS、限流、压缩与安全响应

- **功能名称/模块/目的**：HTTP 安全基线；阻止跨站 Cookie 写入、恶意来源、请求洪泛和超大压缩包。
- **使用者/入口/触发**：全部 HTTP 调用；Fastify Hook 和全局插件自动触发。
- **前置条件/流程**：Web 写请求必须携带与 `APP_ORIGIN` 完全一致的 `Origin`；设备采集使用 Bearer Token；允许无 Origin、App Origin、白名单扩展 Origin，开发环境额外允许 localhost。
- **输入/校验**：全局 300 请求/分钟、ban=3；JSON 解压后 50 MiB；只支持 identity/gzip Content-Encoding；multipart 全局 1 文件、2 GiB，但业务路由另有 512 MiB 限制。
- **输出/规则**：API/health 均 `no-store`；CSP、HSTS（生产）、DENY frame、nosniff、Permissions Policy 等响应头；Zod 为 400 并返回 issues；500 只返回通用错误。
- **状态/权限**：无业务状态；限流状态由插件维护。
- **异常/边界**：不支持的编码 415，解压超限 413，非法 Origin 拒绝；Fastify 全局错误日志刻意不记录可能含敏感参数的完整异常。
- **配置/第三方**：`APP_ORIGIN`、`EXTENSION_ORIGINS`、`TRUST_PROXY`、`NODE_ENV`。
- **接口/实体/代码**：所有接口；`apps/server/src/app.ts:37-177`、`apps/server/src/http.ts:18-106`、`apps/server/test/http-security.test.ts:5-51`。
- **实现状态/可信度**：已实现并有测试，**已确认**。

### 4.1.5 修改密码、两阶段 TOTP、管理员恢复与 Session 管理

- **功能名称/模块/目的**：账号与安全；让唯一管理员在不引入多用户/RBAC 的前提下轮换凭据并远程结束浏览器登录。
- **使用者/入口/触发**：已登录管理员使用“设置 → 账号与安全”；服务器运维者可运行 `admin:recovery` CLI。Web 接口为 `POST /auth/password`、`POST /auth/totp/reset`、`POST /auth/totp/confirm`、`DELETE /auth/totp/pending`、Session 系列接口。
- **前置条件/正常流程**：改密和发起重绑都再次验证当前密码与当前 6 位 TOTP；发起重绑只保存主密钥加密的 pending Secret 并返回 URI，管理员用新验证器生成的 6 位码确认后才原子激活；取消或过期不会影响旧 Secret。Session 可逐个或批量注销。服务器恢复 CLI 需要数据库连接、`APP_MASTER_KEY` 和服务器 Shell，可重置密码、清除 TOTP 或注销全部 Session。
- **输入字段及校验**：currentPassword 1–256、totpCode 精确 6 位数字、新密码 12–256；Session ID 必须 UUID 且属于当前唯一用户。
- **输出/结果**：改密 `{ok:true}`；发起重绑返回 pending secret/otpauthUrl/expiresAt；确认或取消返回成功；Session 删除 204；批量注销返回 revoked 数量；CLI 的 reset-totp 会在可信终端显示新 Secret/URI，另外两个命令只输出结果。
- **业务规则/权限/状态**：只有当前已认证管理员可走 Web 流程；pending Secret 约 10 分钟有效且一次只保留一个；只有新码验证通过才替换 active Secret；改密不自动注销现有 Session；删除当前 Session 会清 Cookie。CLI 属于服务器控制面，不是远程 API。
- **异常与边界**：当前凭据错误不透露具体项；pending 不存在/过期或新码错误返回 400；Session 不存在/不属于本人 404；系统仍没有邮件自助找回，CLI 要求服务器权限并应在可信终端执行。

### 4.3.1 服务端采集、入库脱敏、版本化与幂等

- **功能名称/模块/目的**：统一采集入库；把设备/导入产生的快照可靠转成版本化事实数据。
- **使用者/入口/触发**：任意未撤销配对设备调用 `POST /api/v1/captures`；导入 Worker 内部调用 `ingestCapture(..., null)`。
- **前置条件/流程**：Bearer 设备有效 → 合同 Schema 校验 → 加载自定义规则并执行不可逆入库脱敏 → 对会话、分支、幂等键依次取 PostgreSQL advisory lock → 验证/重建 Delta → upsert Conversation → 插入 Revision、Message、Segment、全文 SearchChunk、CaptureRun，全部处于单次事务。
- **输入字段/校验**：Provider 12 项；Session≤1024、标题≤2048、URL 仅 HTTP(S)、消息 1–100,000、单消息 Segment 1–10,000、单 Segment 合同上限 2,000,000；Idempotency-Key≤512；complete 必须 top/bottom/stable 全真。
- **输出/规则/权限**：新 Revision 201，重复快照 200 `unchanged=true`；Conversation 以 provider+session 唯一；`snapshotHash` 是脱敏且按实际入库长度规范化后的内容身份，`revisionIdentityHash` 再纳入标题/canonical URL，`conversationId + revisionIdentityHash` 唯一。两者都忽略 capturedAt，因此纯标题/URL变化会形成可比较 Revision，同一快照的时间性重试仍幂等；CaptureRun 另存 `payloadIdentityHash`，并兼容升级前只存 snapshotHash 的幂等记录。`contentIntegrityHash` 独立校验可重建正文与 Revision/消息元数据，不把去重身份误作完整性证据。
- **状态变化**：新会话/新 Revision；Delta 逻辑上是完整 Revision，但物理只存 appended body 并指向 base；采集结果 complete/partial/failed；若 `classification.autoOnCapture=true`，新 Revision 成功后异步入队整理，入队失败不回滚归档。
- **异常/边界**：Delta 基线不符 409 并 `requiresFullCapture=true`；其余解析/幂等冲突 400，并尽可能写 failed CaptureRun；Segment 入库再截断：普通/代码/引用 200,000，reasoning 20,000，tool_status 8,000。Revision.searchText 仍为 2,048 字符摘要，但完整消息另切 4,000 字符分块用于全文搜索。

- **前置条件/流程**：HTTP 流式写入共享可写 `RESTORE_STAGING` → 202 返回 restoreJobId → Worker 依次 validating、validated、restoring → 事实表事务提交时原子写入 `factsCommittedAt/rebuilding_search` → 重建检索 → verifying → 完整性检查通过后 completed 并删除 staged 文件。

## 5.1 首次启用与 Web 登录


## 5.2 Chrome 自动采集到归档

```text
管理员生成 chrome_extension 配对码
  → 扩展请求服务器+全部平台Host权限并领取Token
  → 打开受支持会话
  → 2s初检 / 3s路由轮询 / DOM变化4s debounce
  → 若用户正在操作，等待空闲满12s
  → 若生成中，每2s复查
  → 轻量指纹与本地基线比较
      ├─ 首次/分支/适配器变化/手动 → 完整滚动扫描
      ├─ 完整基线后新增消息 → 增量扫描
      ├─ 找不到可信增量基线 → 完整滚动扫描
      └─ 指纹确认未变化 → 跳过
  → IndexedDB Outbox
  → gzip + Bearer + Idempotency-Key 上传
  → 服务端事务式脱敏/幂等/版本化
      ├─ 201新Revision
      ├─ 200重复/元数据修复
      └─ 409增量基线不符 → 扩展强制完整采集
```

归档是主事实；即使采集后自动分类入队失败，新 Revision 仍成功。证据：`apps/extension/entrypoints/content.ts:668-862`、`apps/extension/entrypoints/background.ts:122-213`、`apps/server/src/routes/captures.ts:25-70`。

```text
完整优先Revision
  → 过滤user/assistant并移除推理/工具状态
  → 经济模式判断是否复用稳定结果
  → 本地项目名命中或LLM结构化建议
  → 粗粒度项目阈值决策
  → 标签NFKC/长度/词数/UUID过滤
  → 保留人工项目锁、manual或locked标签
  → 事务写Project Assignment和Auto Tags
  → Task进度更新
```

模型安全/422/格式错误只对当前会话本地降级；额度错误进入 deferred 并按恢复时间续跑；其他错误计入单项失败并继续批次。证据：`apps/server/src/services/analysis.ts:548-1138`。

## 5.5 报告与邮件

```text
手动触发或Cron
  → 建立/复用周期唯一AnalysisRun
  → 取上一完整周/月内complete Revision（每会话最新）

```

## 5.6 ZIP 历史导入

```text
管理员上传ZIP
  → 写Inbox、SHA-256去重
  → ImportJob queued
  → Worker解析格式/ZIP安全限制
  → 每个Snapshot独立调用统一采集
  → 更新 imported/unchanged/failed/total 进度
  → 全成功 completed并移到processed
  → 部分成功 partial / 全失败 failed，并移到failed
  → partial/failed 可手动重试或重传同SHA-256 ZIP
  → Worker重启/孤儿processing由Inbox扫描恢复
```

整个 ZIP 不是全有或全无事务；失败前成功的会话保留，重试靠采集哈希去重。证据：`apps/server/src/jobs/import-job.ts:176-365`。

## 5.7 Web 业务恢复

```text
管理员确认替换
  → HTTP 流式写入共享 Restore staging
  → 返回 202 + restoreJobId
  → Worker validating / validated
  → 旧knowledge兼容丢弃并warning
  → APP_MASTER_KEY不一致则移除加密Setting
  → 恢复前再次执行存储脱敏
  → 规范化旧项目名并处理视觉重复
  → 进入 Maintenance Mode（业务 API 503）
  → PostgreSQL advisory lock
  → 单事务删除并重插18张业务表
  → 提交时原子记录 factsCommittedAt + rebuilding_search
  → 提交前失败整体回滚，状态 failed，退出 Maintenance Mode
  → rebuilding_search
  → verifying 归档完整性
  → 成功 completed，删除 staged 文件并退出 Maintenance Mode
  → 提交后失败 recovery_required，继续 Maintenance Mode
  → 用户重试后只执行 rebuilding_search + verifying
```

替换前可以取消，进入 restoring 后不可取消。pre-commit failed 在配置保留期内保留 staged 文件并允许完整重试；expired failed 由 housekeeping 清理，也可在 Web 删除；recovery_required 不依赖上传文件，只恢复派生检索和完整性验证。管理员账号、当前 Web Session、一次性配对码和 RestoreJob 运维记录保留；Device Token Hash 属于业务备份，会被替换。证据：`apps/server/src/routes/backups.ts`、`services/restore.ts`、`services/backup.ts`、`app.ts`。

# 6. 数据模型与状态流转

## 6.1 核心关系

```text
User 1 ── * WebSession

PairingCode  --claim once--> Device 1 ── * CaptureRun
                                      └── * ConversationRevision (source可置空)

Conversation (provider + externalSessionId 唯一)
  ├── * ConversationRevision (conversation + revisionIdentityHash 唯一；snapshotHash为内容身份)
  │     ├── 0..1 baseRevision ── 形成 snapshot/delta 链
  │     └── * Message ── * MessageSegment
  │              └── * ConversationSearchChunk（派生全文索引）
  ├── 0..1 ConversationProject ── 0..1 Project
  └── * ConversationTag ── 1 Tag

AnalysisRun --produces--> Report
BackgroundTask = classification_rebuild | storage_redaction | archive_integrity
ImportJob --ingests--> Conversation/Revision
RestoreJob --tracks--> staged backup → restore phases
Setting / RedactionRule / SavedSearch / OperationLog 为系统配置、常用视图与审计
```

表定义证据集中在 `apps/server/src/schema.ts`；Migration 0012 先建标签表再删除旧 `knowledge_items`，0016增加项目规范名，0017增加导入重试字段，0018增加全文分块、Saved Search 和回收站索引，0019增加 pending TOTP、Revision历史元数据、设备/适配器健康、邮件投递和 RestoreJob，0020增加独立内容完整性哈希，0021固化Restore提交边界，0022治理存量视觉重复标签；均不删除归档事实链。

## 6.2 关键状态机

| 实体 | 状态流转 | 规则/终态 |
| --- | --- | --- |
| Web实例 | uninitialized → initialized | 只能一次；无反向流程 |
| TOTP Secret | active；active + pending → active(new) 或 pending cancelled/expired | 新码确认前旧密钥始终有效；pending约10分钟 |
| WebSession | absent → active → expired/deleted | 30天；logout/远程注销；每日清理过期记录 |
| PairingCode | active → claimed，或 active → expired | 10分钟、单次、kind匹配；每日清理历史记录 |
| Device | active → revoked → deleted | 第一次DELETE撤销，第二次永久删；无恢复 |
| Capture/Revision | none → partial/complete；重复→unchanged | complete必须top/bottom/stable；Delta只能基于complete；failed仅CaptureRun |
| Conversation | absent → active → trashed → active/deleted | 30天可恢复；确认/到期永久删；重采可恢复同一记录 |
| Project | active ↔ archived → merged/deleted | 归档保留关系；合并不可逆 |
| Project Assignment | none/unclassified ↔ assigned；auto ↔ locked | locked confidence=1；auto可被AI改；一个会话最多一条 |
| ConversationTag | absent → manual+locked ↔ auto+unlocked → removed | 交还AI时真实转换source并入队整理 |
| AnalysisRun | queued → running → completed/failed；running→queued(deferred) | kind+window唯一；failed可手动重排 |
| BackgroundTask | queued → running → completed/failed | stale无live job才自动失败；deferred不按30分钟误杀 |
| ImportJob | queued → processing → completed/partial/failed；partial/failed → queued(retry) | 同hash复用记录重试；attempt/lastRetryAt追踪 |
| Storage Redaction | queued → running → completed/failed | 替换不可逆，无undo |
| Archive Integrity | queued → running → completed/failed | 只读检查；无独立内容哈希的旧/合法脱敏 Revision 计为 unverifiable，不伪造失败 |
| RestoreJob | queued → validating → validated → restoring → rebuilding_search → verifying → completed；pre-commit→failed；post-commit→recovery_required | restoring前可取消；failed完整重试；recovery_required只重建/验证且持续维护模式 |

## 6.3 Revision 选择规则

- 列表、详情默认、分类、导出、Dashboard多处均采用“**complete优先**，然后 capturedAt/createdAt 新者优先”，不是简单最后上传；部分采集不会覆盖已有完整基线的默认显示。证据：`apps/server/src/routes/conversations.ts:157-168`、`apps/server/src/services/capture.ts:357-378`。
- 项目时间线再以 revisionId 解决时间戳并列，保证稳定顺序。证据：`apps/server/src/routes/projects.ts:336-345`。
- Delta Revision 的 `messageCount` 是逻辑总数，物理 Message 行只含 appended 部分；读取必须沿 `baseRevisionId` 还原。证据：`apps/server/src/services/capture.ts:655-700`、`apps/server/src/services/revision-storage.ts:21-99`。

# 11. 疑似未完成或存在问题的功能

## 11.1 前后端与产品入口不一致

README 与编号中文 `docs` 已于 2026-08-27 同步为当前代码口径；下列仍是产品实现本身的差异：

1. **Chrome 豆包支持并未实现（已确认）**：协议和会话 Web 筛选确有 `doubao`（`packages/contracts/src/index.ts:8`、`conversations.ts:73-83`），但 `wxt.config.ts:23-36`、`content.ts:16-29`、`adapters/definitions.ts`均无豆包域名/适配器。服务端可接收其他客户端或历史导入提交的豆包数据，当前 Chrome 不能采。
2. **`importer` 设备类型无产品入口/客户端（已确认/待确认）**：合同/后端允许，Web只列Chrome和本地同步。

## 11.2 明确的产品/实现缺口或潜在缺陷

1. **Restore Worker 仍有内存上限（已确认）**：HTTP 上传已流式化、恢复已任务化，但 Worker 会把 staged 压缩文件和解压 JSON 载入内存；512 MiB/1 GiB 上限下仍应做大备份压力测试。
2. **Activity 的采集异常是聚合摘要（已确认）**：近24小时异常只产生一项，且 summary 基于当前合并窗口；不能代替日志、Adapter Health 或完整性检查。
3. **中文全文检索主要依赖 ILIKE（已确认）**：`simple` tsvector 对英文等分词内容有利，连续中文仍走字面回退；已提供 benchmark 命令，但尚无目标百万级数据的实测基线。
4. **项目 overview 仍需做聚合压测（较可能）**：overview 已只返回统计，项目/未归类数据已分页，但统计 SQL 在数万项目/关系下仍需验证。
5. **批量操作上限500且无批量永久删除（已确认/有意限制）**：超过500需分批，危险删除只能逐条进入回收站再确认。
6. **导入 ZIP 不是总事务（已确认/有意语义）**：已通过 partial 与精确统计向用户暴露，重试靠 snapshotHash 幂等；调用方不能把 failed/partial 理解为零写入。
7. **归档完整性检查是诊断而非自动修复（已确认/有意限制）**：发现断链、孤儿或 hash mismatch 后不会猜测性修改事实档案，需要从备份/源端重新采集或人工处置。
